村瀬用｜Django グルメ店決めアプリ 開発担当メモ
作成日：2026年9月17日
担当：店舗・評価・評価理由・候補絞り込み・再検索

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. アプリの目的と今回の完成ライン
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
複数人の希望や店舗評価を集め、みんなで食事に行く店を決めるWebアプリです。

基本の流れ：
グループ作成 → メンバー参加 → 各自の希望条件入力
→ 候補店舗表示 →「いい／どちらでもない／いや」で評価
→「いや」の理由を集計 → 条件調整・候補再検索
→ 最終候補の確定 → 最終投票 → 店舗決定・結果表示

【決まっている方針】
・開発にはDjangoを使います。
・村瀬：Restaurant / Evaluation / EvaluationReason / 候補絞り込み / 再検索。
・佐々木：Group / GroupMember / UserPreference / Vote / 最終結果。
・外部店舗APIは後回しにします。まずダミー店舗データで最後まで動かします。
・評価は3段階。「いや」の理由は、高い・遠い・雰囲気が嫌・メニューが微妙・その他を想定します。

【このメモの位置づけ】
以下のapp構成、Modelの項目、View名、候補数、集計方法、進行ルールは実装案です。
既に確定した仕様ではありません。着手時に2人でそろえ、変更時は相手にも共有してください。
デザイン・仕様整理・コードレビューは依頼者が担当する前提です。

完成は2段階で考えます。
・最初の通し動作：ダミー店舗を表示し、評価・単純な絞り込み・投票・結果までつなぐ。
・MVP完了：上記に、評価理由を使った簡単な条件調整とダミーデータの再検索を加える。
  外部API、高度な自動最適化、実際の経路距離計算はMVPの完了条件に含めません。

2. 村瀬の担当範囲
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
条件を受け取ってから、最終投票に渡す候補を作るまでを担当します。

・ダミー店舗データの準備、登録方法の共有。
・佐々木が保存した希望条件の取得・集約。
・条件に合う店舗の抽出、候補一覧・店舗情報の表示。
・EvaluationとEvaluationReasonの登録・更新。
・店舗ごとの評価数・理由・点数の集計。
・単純なルールでの候補絞り込み。
・評価理由を反映した検索条件の調整と、ダミーデータからの再検索。
・ラウンドごとの候補・条件の保存。
・佐々木の最終投票に渡す候補の確定・取得処理。

佐々木に任せる範囲：
・グループ作成・参加・所属確認・本人の希望条件入力。
・Groupの進行状態を変更する共通処理。
・最終候補の投票画面、Vote、投票集計、同票処理、最終結果。

難易度の目安：ダミー店舗表示は低、評価・理由保存と集計は中、
条件更新・再検索と外部APIは高です。難しい処理は後半に回します。

3. Django app / Model の例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
MVPでは3つのappにまとめる案です。

config/       共通設定と全体URL
groups/       佐々木：Group、GroupMember、UserPreference
restaurants/  村瀬：Restaurant、Evaluation、EvaluationReason、候補管理
voting/       佐々木：Vote、最終結果
templates/    各appの画面と共通レイアウト
static/       CSSなど

最初はevaluations/を独立させず、restaurants/内にまとめて構いません。
ユーザー識別はDjango標準認証を使う案です。佐々木が用意するUserと所属確認を使い、
独自のUserやGroupを重複して作りません。User参照はsettings.AUTH_USER_MODELを使います。

【restaurants.Restaurant】
役割：検索・評価・投票で共通に参照する店舗。
項目例：name、address、genre、price、distance、business_hours。
priceは1人あたりの目安・円、distanceは共通デモ地点からの距離・m。
ダミー値であることを画面に明記し、現実の現在地・営業時間の判定とは区別します。
店舗IDは再表示や再検索で変えず、Voteからも同じ店舗を参照できるようにします。

【restaurants.Evaluation】
役割：誰が、どのグループの何回目の候補として、どの店をどう評価したか。
項目例：group、user、restaurant、round、value、created_at、updated_at。
value：GOOD（いい）/ NEUTRAL（どちらでもない）/ BAD（いや）。
group・user・restaurant・roundの組み合わせは1件のみとし、再送信は更新します。
点数はModelに固定せず、valueを保存して集計処理で点数に変換します。

【restaurants.EvaluationReason】
役割：BADの具体的な理由。
項目例：evaluation、reason、comment（必要な場合）。
reason例：EXPENSIVE / FAR / ATMOSPHERE / MENU / OTHER。
複数理由を選択可能にし、Evaluation 1件に対して理由を複数行保存する案です。
同じevaluationとreasonは重複させません。
BADは理由を1つ以上必須とし、GOODやNEUTRALへ変更した場合は以前の理由を削除します。
「その他」の自由記入を必須にするかは着手時に決めます。

【restaurants.CandidateRound：補助Model案】
役割：各グループ・各ラウンドの検索条件と候補をDBに保存。
項目例：group、round、search_conditions、candidates、final_candidates、created_at。
groupとroundの組み合わせは1件のみ。
candidatesとfinal_candidatesはRestaurantへの別々の多対多参照にする案です。
final_candidatesはcandidatesの部分集合に限定します。
保存方法は他の設計でも構いませんが、「店舗マスタ」と「今回の候補集合」は区別します。
検索条件には集約した上限や順位付けの方針を保存し、本人の希望条件は残します。
この補助Modelや取得処理は村瀬が担当します。

4. View / Template / URL の例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
View名は例です。クラスベースでも関数ベースでも、2人で方針をそろえれば構いません。
DjangoのフォームとTemplateで実装でき、REST APIの別途作成は必須ではありません。

RestaurantCandidateListView
  templates/restaurants/candidate_list.html
  /groups/<group_id>/restaurants/：現在ラウンドの候補と評価状況。

CandidateSearchView
  /groups/<group_id>/search/：最初の候補生成をPOSTで実行。

EvaluationCreateUpdateView
  templates/restaurants/evaluation_form.html
  /groups/<group_id>/restaurants/<restaurant_id>/evaluate/：評価と理由の入力。

EvaluationSummaryView
  templates/restaurants/evaluation_summary.html
  /groups/<group_id>/evaluations/summary/：評価数、理由、未評価者、順位。

CandidateRefineView
  templates/restaurants/refine.html
  /groups/<group_id>/refine/：調整する条件の表示・確認後の再検索。

FinalCandidateConfirmView
  /groups/<group_id>/candidates/finalize/：最終候補の保存と投票段階への移行。

一覧表示はGET、評価保存・候補生成・再検索・最終候補確定はPOSTに分けます。
再読み込みのたびに勝手に候補やラウンドを作り直さないでください。
検索・集計・絞り込みはservices.py等にまとめると、Viewと分けて確認しやすくなります。

5. 検索・絞り込みの最小ルール案
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
まずは動作を説明できる単純なルールにします。数値や件数はチームで調整可能です。

【ダミー店舗】
・予算・距離・ジャンルが異なる店舗を10〜20件ほど用意。
・fixtureまたは管理コマンドで、2人が同じデータを再現できるようにする。
・最初の表示件数は最大10件、最終候補は最大3件の案。

【初回の検索】
・全員の希望条件がそろってから検索する。
・budget_maxとdistance_maxは、それぞれ全員の上限の最小値を使う案。
・priceが予算内、distanceが距離内の店舗を候補にする。
・0件なら「条件に合う店舗がありません」と表示し、条件を勝手に緩めない。
  最初の検索が成立しない場合は参加・条件入力段階を維持して見直せるようにする。

【評価と集計】
・GOOD=+2、NEUTRAL=+1、BAD=-2として、店舗ごとの合計点を計算する案。
・「未評価」はNEUTRALと区別し、全員の評価がそろうまでは待ち状態を表示。
・同点ならBADの少ない店を優先し、さらに同じなら店舗ID順で安定させる案。
・この点数は候補の順位付け用で、最終投票の票数とは別物。
・合意度を表示する場合は、GOODの人数／対象メンバー数など定義を明記する。
  専用の高度な合意度指標はMVP必須ではない。

【理由を使った再検索】
・最初のMVP案では「高い」「遠い」を集計し、次回の並び順を調整する。
・「高い」が多ければ価格の安い順、「遠い」が多ければ距離の近い順にする案。
・両者の件数が同じ場合は価格→距離→店舗ID順とする案。
・雰囲気・メニュー・その他も保存・表示するが、意味の自動推定は後回し。
・前回BADが付いた店を次回候補から一旦除外し、ダミーデータ全体から探し直す案。
・全員の予算・距離上限は引き続き守る。元のUserPreferenceは変更しない。
・前回と異なる次回候補が1件以上得られたら、その条件・候補の保存とラウンド更新を
  まとめて実行し、新しいラウンドで再評価する。
・0件なら新ラウンドに進めず、現在候補を残して、除外条件の見直しや
  現在候補から最終投票に進む操作を作成者に示す。
・候補集合が変わらない場合は「新しい候補なし」と表示する。
  並び順だけの変化ではラウンドを進めず、現在の候補・評価・roundを維持する。

この段階では、検索条件の調整は「並び順・除外条件の更新」で成立させます。
予算上限の自動引き下げ、雰囲気やメニューの類似度計算は後から追加できます。

【最終候補】
・現在ラウンドの評価がそろったら、作成者が再検索か最終候補確定を選ぶ。
・最終候補確定では、現在候補から評価順位上位の最大3件を保存。
・1〜2件しかなければ、その件数で進める。0件では投票を開始しない。
・BADは順位・次回検索に反映する案であり、最終投票に対する絶対的な拒否権ではない。
  絶対に除外したい条件を扱う場合は、別途仕様を決める。
・votingに進んだ後は候補集合を固定し、再評価・再検索を受け付けない。

6. 他担当との境界と受け渡し
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【佐々木から受け取る】
group_id、参加メンバー、各メンバーのUserPreference、現在の進行状態。
希望条件例：group_id=10、user_id=3、budget_max=2000、distance_max=1000。
budget_maxは円／1人、distance_maxは共通デモ地点からのmにそろえます。
本人の条件入力・更新は佐々木、全員分の集約と検索への適用は村瀬です。

【佐々木へ返す】
group_id、round、確定したRestaurantのID一覧、画面表示用の店舗情報。
例：group_id=10、round=2、final_candidate_ids=[101, 104, 108]。
候補の実体をDBに保存し、ブラウザからのID一覧ではなく保存済み集合を返します。
取得処理の例：restaurants/services.py の get_final_candidates(group)。
佐々木はその集合への所属を検証してVoteを受け付けます。
最終投票用の店舗Modelや独自の店舗IDを別途作らないようにします。

【進行状態】
Groupのstatusとcurrent_round、状態変更の窓口は佐々木が担当。
村瀬は候補生成・再検索・最終候補確定のタイミングでその窓口を呼びます。
候補の保存と状態変更をまとめて成功・失敗させ、半端な状態を残しません。
最終候補の保存とvotingへの移行をそろえ、投票開始後は候補を変更しません。

【共通の進行ルール案】
・初回候補を1件以上保存できた時点で、対象メンバー・条件を固定する。
  このときcollecting／round=0からevaluating／round=1へ移行する。
  初回0件ならcollecting／round=0のまま、参加・本人の条件更新を許可する。
・全員の条件入力がそろったら作成者が検索を開始。
・全員が現在の全候補を評価したら、作成者が再検索か最終候補確定を選ぶ。
・最終投票は1人1票。全員投票前は本人の票を更新可能。
・全員投票で受付終了。単独最多を確定し、同票なら作成者が同票店舗から選ぶ。
・決定後の再投票・再開はMVP対象外。
投票集計や同票処理は佐々木が実装し、村瀬側には重複実装しません。

7. 実装する順番
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Step 0｜共通準備［2人で実施］
・3 app構成、User、Modelの参照関係、単位、進行ルールを確認。
・共通設定、全体URL、base.htmlの編集担当とmigrationの共有方法を決める。

Step 1｜店舗を表示する［低］
・Restaurant、migration、admin、ダミーデータを用意。
・候補一覧を表示し、店舗IDと必要な表示項目を佐々木に渡す。
・この段階では外部APIを接続しない。

Step 2｜希望条件と接続する［中］
・佐々木のGroupとUserPreferenceから検索条件を作る。
・CandidateRound等で今回の候補を保存し、予算・距離による検索を動かす。

Step 3｜評価・理由を保存する［中］
・Evaluation、EvaluationReason、入力画面を作る。
・3段階評価、複数理由、更新、未評価表示、ラウンド分離を確認。

Step 4｜集計・最終候補を渡す［中］
・単純な点数で並べ、上位最大3件を確定する。
・佐々木の投票・結果と接続し、最初の通し動作を完成。

Step 5｜ダミーデータで再検索する［高］
・理由集計から並び順・除外条件を更新し、次の候補を保存する。
・ラウンドを進めて再評価できるようにする。
・候補0件、新しい候補なし、古い画面からの送信を処理する。

Step 6｜MVP統合確認［2人で実施］
・条件入力 → 評価 → 1回再検索 → 最終候補 → 投票 → 結果を実演。
・依頼者に画面と一連の動作をレビューしてもらう。

Step 7｜MVP後
・採用する店舗APIと取得項目、利用条件を確認して接続する。
・外部店舗IDと内部Restaurant IDの対応、欠損項目、失敗時の表示を設計する。
・検索の入口を共通化し、ダミーデータ取得部分を外部APIに置き換えられるようにする。
・高度な条件更新、地図・距離計算などは必要性を確認して順に追加する。

8. 実装時の注意点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
・userはログイン情報から取得し、所属・現在ラウンド・今回の候補かを処理側で検証する。
・集計は必ずgroupとroundで絞る。他グループや過去ラウンドの評価を混ぜない。
・未評価をNEUTRALとして扱わない。評価者数と対象メンバー数を別々に確認する。
・評価と理由はまとめて保存し、更新時の理由の残り・重複を防ぐ。
・古い画面からの評価送信や、投票開始後の再検索を拒否する。
・再検索の二重送信で同じラウンドが複数作られないようにする。
・候補生成と進行状態変更はトランザクション等で整合性を保つ。
・「高い」という意見だけから料理ジャンルまで変更しない。
・ユーザーの元の希望条件を、集約条件・再検索条件で上書きしない。
・外部APIを前提にした開発や、先回りした複雑な推薦ロジックから始めない。
・共有設定やmigrationの競合を避け、別appへの参照を両方の環境で確認する。

9. 村瀬の完了条件
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
□ ダミーデータを再現可能な方法で投入し、外部APIキーなしで候補を表示できる。
□ 全員の希望条件を使って、予算・距離に合う店舗を抽出できる。
□ 3段階評価と複数の理由を保存・更新できる。
□ BAD以外への変更で、以前の理由が残らない。
□ 未評価を区別し、評価数・理由・順位を正しく表示できる。
□ group・round単位で候補と評価が分離されている。
□ 理由に応じた条件調整で、ダミーデータから少なくとも1回再検索できる。
□ 候補0件・新しい候補なしでも進行不能や無限ループにならない。
□ 最新ラウンドの最終候補を保存し、佐々木が同じ集合を取得できる。
□ 投票開始後の候補変更、過去ラウンドへの送信、対象外店舗の評価を拒否できる。

共同の確認シナリオ：
3人参加 → 条件入力 → ダミー店舗を評価 →「高い」などの理由で1回再検索
→ 最新の候補から最大3件を確定 → 全員投票 → 同じ決定店舗を全員が閲覧。
別途、候補0件、未評価・未投票、同票、二重送信、グループ間の混入がないことを確認します。

候補を保存・取得する方法／進行状態の更新窓口／共通ファイルの編集担当。
