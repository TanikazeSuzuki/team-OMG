佐々木用｜Django グルメ店決めアプリ 開発担当メモ
作成日：2026年9月17日
担当：グループ・参加・希望条件・最終投票・最終結果

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. アプリの目的と今回の完成ライン
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
複数人の希望や店舗評価を集め、みんなで食事に行く店を決めるWebアプリです。

基本の流れ：
グループ作成 → メンバー参加 → 各自の希望条件入力
→ 候補店舗表示 →「いい／どちらでもない／いや」で評価
→「いや」の理由を集計 → 条件調整・候補再検索
→ 最終候補の確定 → 最終投票 → 店舗決定・結果表示

【決まっている方針】
・開発にはDjangoを使います。
・佐々木：Group / GroupMember / UserPreference / Vote / 最終結果。
・村瀬：Restaurant / Evaluation / EvaluationReason / 候補絞り込み / 再検索。
・外部店舗APIは後回しにします。まずダミー店舗データで最後まで動かします。
・評価は3段階。「いや」の理由は、高い・遠い・雰囲気が嫌・メニューが微妙・その他を想定します。

【このメモの位置づけ】
以下のapp構成、Modelの項目、View名、候補数、集計方法、進行ルールは実装案です。
既に確定した仕様ではありません。着手時に2人でそろえ、変更時は相手にも共有してください。
デザイン・仕様整理・コードレビューは依頼者が担当する前提です。

完成は2段階で考えます。
・最初の通し動作：ダミー店舗を表示し、評価・単純な絞り込み・投票・結果までつなぐ。
・MVP完了：上記に、評価理由を使った簡単な条件調整とダミーデータの再検索を加える。
  外部API、高度な自動最適化、実際の経路距離計算はMVPの完了条件に含めません。

2. 佐々木の担当範囲
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
入口と出口を担当します。

入口：
・グループ作成、参加用URLまたはコードの発行。
・グループへの参加、参加メンバー一覧。
・本人の希望条件の入力・更新・保存。
・全員が条件を入力済みかの表示。
・グループ所属の確認と、進行状態を変更する共通処理。

出口：
・村瀬が確定した最終候補の表示。
・最終投票の登録・更新・集計。
・未投票者の表示、同票時の処理、決定店舗の保存・結果表示。

村瀬に任せる範囲：
・店舗データの整形と検索、評価・評価理由の保存。
・評価集計、候補の順位付け、条件調整、再検索。
・最終投票へ渡す店舗集合の作成・保存。

難易度の目安：グループ作成は低、参加・条件保存は低〜中、
投票・状態管理・同票処理は中です。検索処理を待たずに入口から進められます。

3. Django app / Model の例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
MVPでは3つのappにまとめる案です。

config/       共通設定と全体URL
groups/       佐々木：Group、GroupMember、UserPreference
restaurants/  村瀬：Restaurant、Evaluation、EvaluationReason、候補管理
voting/       佐々木：Vote、最終結果
templates/    各appの画面と共通レイアウト
static/       CSSなど

preferences/ や evaluations/ を最初から独立させる必要はありません。
ユーザー識別はDjango標準認証を使う案とし、MVPではテストユーザーでも構いません。
ログイン画面などの入口は佐々木が用意し、村瀬は同じUserを参照します。
独自Userモデルが必要かは最初のmigration前に決めます。
他ModelからのUser参照にはsettings.AUTH_USER_MODELを使います。

【groups.Group】
役割：食事の店を決める1つの部屋。
項目例：name、created_by、join_code、status、current_round、created_at。
status案：collecting（参加・条件入力）/ evaluating（評価・再検索）
          / voting（最終投票）/ decided（決定済み）。
current_round案：開始前は0、初回候補の保存成功で1、再検索の保存成功ごとに増やす。

【groups.GroupMember】
役割：誰がどのグループに参加しているかを保存。
項目例：group、user、joined_at。
同じgroupとuserの組み合わせは1件のみ。作成者もメンバーに登録します。

【groups.UserPreference】
役割：グループごとの本人の希望条件。
項目例：group、user、budget_max、distance_max、updated_at。
同じgroupとuserの組み合わせは1件のみ。再送信は重複作成せず更新します。
budget_maxは1人あたりの予算上限・円、distance_maxは基準地点からの距離上限・m。
最初はこの2項目に絞り、ジャンル、営業中、NG条件は追加候補として扱います。
距離の基準地点は共通のデモ地点に固定し、画面に明記する案です。

【voting.Vote】
役割：最終候補に対する1人1票。
項目例：group、user、restaurant、created_at、updated_at。
同じgroupとuserの組み合わせは1件のみ。
restaurantは村瀬のRestaurantを参照し、独自の店舗Modelは作りません。
このMVP案では1グループにつき最終投票は1回とし、投票開始後の再検索は行いません。

【voting.Result：補助Model案】
役割：確定した結果を保存し、再表示しても決定店舗が変わらないようにする。
項目例：group（1対1）、restaurant、decided_at。
保存方法は他の設計でも構いませんが、決定後に毎回選び直す実装にはしません。

4. View / Template / URL の例
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
View名は例です。クラスベースでも関数ベースでも、2人で方針をそろえれば構いません。
DjangoのフォームとTemplateで実装でき、REST APIの別途作成は必須ではありません。

GroupCreateView
  templates/groups/create.html
  /groups/new/：作成フォーム表示・作成。

GroupJoinView
  templates/groups/join.html
  /groups/join/：コード入力・参加。

GroupDetailView / GroupMemberListView
  templates/groups/detail.html
  /groups/<group_id>/：参加者、入力状況、現在の進行段階。

PreferenceCreateUpdateView
  templates/groups/preference_form.html
  /groups/<group_id>/preferences/：本人の条件入力・更新。

FinalCandidateView
  templates/voting/final_candidates.html
  /groups/<group_id>/vote/：固定済み最終候補と投票フォーム。

VoteCreateUpdateView
  上記の投票フォームからPOSTを受け取り、保存後に画面へ戻す。

ResultView / ResultConfirmView
  templates/voting/result.html
  /groups/<group_id>/result/：進捗、同票の表示、決定結果。
  同票時の作成者による確定操作はPOSTで扱います。

表示はGET、データの保存・参加・確定などの変更はPOSTに分けます。
共通のtemplates/base.htmlは依頼者のデザインに合わせ、共同で使います。

5. 他担当との境界と共通ルール案
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【佐々木 → 村瀬】
渡すもの：group_id、参加メンバー、各メンバーのUserPreference、現在の進行状態。
希望条件の入力画面と保存は佐々木、全員の条件の集約・検索への適用は村瀬です。
村瀬は本人のUserPreferenceを上書きせず、検索用の条件を別に作ります。

条件の受け渡し例：
  group_id=10、user_id=3、budget_max=2000、distance_max=1000
金額と距離の単位、必須項目、未入力時の扱いを最初に固定します。

【村瀬 → 佐々木】
渡すもの：group_id、round、確定したRestaurantのID一覧、画面表示用の店舗情報。
例：group_id=10、round=2、final_candidate_ids=[101, 104, 108]。
候補の実体はDBに保存します。ブラウザから送られたID一覧を正として扱いません。
最終候補を読む窓口の例：restaurants/services.py の get_final_candidates(group)。
佐々木の投票処理は、必ずこの確定済み集合に含まれる店舗かを検証します。

【進行状態の担当】
GroupのModelと状態変更の窓口は佐々木が担当します。
村瀬は候補生成・再検索・最終候補確定の際に、その窓口を呼び出します。
候補の保存と状態変更はまとめて成功・失敗するようにし、半端な状態を残しません。
最終候補の保存とvotingへの移行をそろえ、投票開始後は候補を変更しません。

【進行ルールの暫定案】
・初回候補を1件以上保存できた時点で、対象メンバー・条件を固定する。
  このときcollecting／round=0からevaluating／round=1へ移行する。
  初回0件ならcollecting／round=0のまま、参加・本人の条件更新を許可する。
・全員の条件入力がそろったら、作成者が最初の検索を開始。
・現在の全候補に全員が評価するまで、村瀬側は未評価を表示。
・評価がそろったら、作成者が再検索か最終候補確定を選択。
・最終候補は最大3件。0件では投票を開始しない。
・再検索で0件なら現在の候補とroundを維持する。村瀬側で除外条件を見直すか、
  作成者が現在候補から最終候補を確定する。本人の希望条件は上書きしない。
  候補集合が変わらない場合も、現在の候補・評価・roundを維持する。
・最終投票は1人1票。全員の投票完了前は本人の票を更新可能。
・全員が投票した時点で受付を締め切る。単独最多ならその店を確定。
・最多が同票なら同票店舗だけを表示し、作成者が1店を選んで確定。
・未投票を0点扱いして勝手に確定しない。決定後の再投票・再開はMVP対象外。

集計点数や再検索の方法は村瀬側の担当です。
佐々木側で独自に候補を並べ替えて投票対象を増減しないでください。

6. 実装する順番
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Step 0｜共通準備［2人で実施］
・3 app構成、User、Modelの参照関係、単位、進行ルールを確認。
・Djangoプロジェクト、設定、全体URL、base.htmlの編集担当を決める。
・Model変更とmigrationをまとめて共有する運用を決める。

Step 1｜データの土台［低〜中］
・Group、GroupMember、UserPreferenceを作成。
・migrationを適用し、adminで登録・関連の確認ができるようにする。
・ログインしたユーザーを識別し、所属確認に共通で使える処理を用意。

Step 2｜グループ作成・参加［低〜中］
・作成、コード発行、参加、メンバー一覧を実装。
・同じ人の二重参加、無効コード、他グループの閲覧を確認。

Step 3｜希望条件入力［低〜中］
・本人の条件を保存・更新。正の数かなどをチェック。
・未入力者を表示し、全員そろったら村瀬の候補表示へつなぐ。

Step 4｜投票側を先行実装［中］
・村瀬が登録したダミーRestaurantと仮の最終候補を使い、
  Vote、投票画面、集計、結果保存・表示を作る。
・店舗Modelや候補管理を自分側に複製しない。

Step 5｜最初の通し動作［2人で実施］
・条件入力 → ダミー候補 → 評価 → 単純な絞り込み → 投票 → 結果を接続。
・「どの画面から次へ進むか」「入力待ちをどう表示するか」をそろえる。

Step 6｜再検索を含むMVP完成［2人で実施］
・村瀬のダミーデータ再検索を接続し、最新ラウンドの最終候補だけに投票。
・候補固定、未投票、同票、決定後の変更禁止を確認。
・依頼者に画面と一連の動作をレビューしてもらう。

Step 7｜MVP後
・外部店舗API接続は村瀬中心で実施。
・佐々木は候補の表示項目変更など、接点に必要な対応をする。

7. 実装時の注意点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
・userはログイン情報から取得し、フォームのuser_idをそのまま信用しない。
・閲覧・更新の両方で所属を確認し、本人以外の希望条件・投票を変更させない。
・グループ作成者だけが行える操作は、画面表示だけでなく処理側でも制限する。
・参加、希望条件、投票の重複はDBの一意制約でも防ぐ。
・投票時は所属・voting状態・受付中・最終候補内かをまとめて検証する。
・同時送信や二重クリックでも票や結果が増えないようにする。
  投票受付と確定の処理はトランザクション等で整合性を保つ。
・POSTフォームにはCSRF対策を入れ、保存後はリダイレクトする。
・投票中・決定済みの候補店舗を削除して結果の参照を壊さない。
・他担当のModel項目名や候補取得処理を変えるときは、先に影響を共有する。
・共有設定やmigrationの競合を避け、別appへの参照を両方の環境で確認する。

8. 佐々木の完了条件
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
□ 作成者を含む3人のテストユーザーで、グループ作成・参加・一覧表示ができる。
□ 各自の予算・距離を保存・更新でき、他人の条件は変更できない。
□ 二重参加・条件の重複保存・二重投票が発生しない。
□ 未入力者・未投票者と、現在の進行段階が分かる。
□ 村瀬の確定した候補だけを表示し、その中から1人1票を保存できる。
□ 対象外店舗、別グループ、受付終了後への投票を拒否できる。
□ 全員投票後の集計、同票時の処理、結果の固定・再表示ができる。
□ 再検索後の最新候補を使い、古い候補への投票を受け付けない。
□ 外部APIキーなしで、条件入力から店舗決定までの実演ができる。
□ 起動方法、migration、テストユーザー、確認手順を共有している。

共同の確認シナリオ：
3人参加 → 条件入力 → ダミー店舗を評価 →「高い」などの理由で1回再検索
→ 最新の候補から最大3件を確定 → 全員投票 → 同じ決定店舗を全員が閲覧。
別途、候補0件、未評価・未投票、同票、二重送信、グループ間の混入がないことを確認します。

着手時にそろえる項目：
認証方法／金額・距離の単位／候補数／集計・同票ルール／
候補を保存・取得する方法／進行状態の更新窓口／共通ファイルの編集担当。
